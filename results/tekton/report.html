Integration Surface

Level 2 — Native
▼

What we observed

Tekton natively emits traces via the OTel Go SDK (go.opentelemetry.io/otel v1.43.0) using OTLP HTTP (otlptracehttp), configured via the config-observability ConfigMap. Both http/protobuf and grpc protocols are supported. 1,262 spans were confirmed flowing across 9 distinct traces.

Metrics are natively exposed on Prometheus endpoint (port 9090) from four services. The same ConfigMap also supports metrics-protocol: grpc and metrics-protocol: http/protobuf for direct OTLP metric export — the Prometheus path was used in this evaluation. No OTLP log export is supported; logs use zap to stdout only.

What's working well

  • Traces emitted natively via OTLP HTTP without requiring a sidecar or agent
  • Both OTLP HTTP and gRPC supported for traces and metrics
  • Dual OTLP export paths give operators architectural flexibility
  • OTel SDK is current at v1.43.0
  • Integration documented in docs/metrics.md and docs/metrics-migration-otel.md

Opportunities

  • Adding OTLP log export (even opt-in) would complete the three-signal story
  • Making OTLP the default for metrics (rather than Prometheus) would streamline the collection architecture
  • Supporting standard OTEL_* environment variables alongside ConfigMap configuration would improve operator ergonomics

Checklist

  • Project emits at least one signal via OTLP natively (traces via OTLP HTTP)
  • OTLP is the primary recommended path for traces
  • Metrics can also be exported via OTLP (gRPC or HTTP) — documented and supported
  • Integration is documented in official project docs
  • No OTLP log export
  • No OTEL_* environment variable support (configuration is ConfigMap-only)
  • Metrics default to Prometheus, not OTLP

Semantic Conventions

Level 1 — Aligned
▼

What we observed

Tekton's own span attributes use custom keys: pipelinerun, taskrun, namespace — rather than established OTel semantic convention keys. All 1,137 child spans carry zero attributes. The instrumentation scope has no version set, and the schema URL references the outdated semconv/v1.12.0 despite using OTel SDK v1.43.0.

On the positive side, the HTTP client/server metrics from otelhttp instrumentation use current semconv attribute names (http_request_method, server_address, http_response_status_code, etc. — the Prometheus underscore format of dot-separated OTel names). No deprecated attributes such as http.method or http.status_code are present.

What's working well

  • No deprecated HTTP semantic convention attributes observed
  • HTTP client/server metrics use current semconv attribute names (http_request_method, server_address, url_scheme)
  • Metric labels are semantically meaningful: status, namespace, pipeline, task

Opportunities

  • Adopt semconv-aligned span attribute keys (e.g., k8s.namespace.name instead of namespace)
  • Add attributes to child spans — currently 1,137 spans carry no attributes at all
  • Update the semconv import from v1.12.0 to v1.26.0+ to reflect the current schema URL
  • Set a version on the instrumentation scope (PipelineRunReconciler, TaskRunReconciler)
  • Align metric names to OTel dot-notation when using OTLP export path

Checklist

  • No deprecated HTTP semantic convention attributes observed
  • HTTP client/server metrics use current semconv attribute names
  • Metric attributes are semantically meaningful (status, namespace, pipeline, task)
  • Custom span attribute keys (pipelinerun, taskrun, namespace) instead of semconv keys
  • All spans are INTERNAL kind regardless of operation type
  • Instrumentation scope has no version set
  • Schema URL references outdated semconv v1.12.0 (should be v1.26.0+)
  • Child spans have no attributes at all
  • Metric names use Prometheus underscore convention (acceptable for Prometheus path but not OTel-native)
  • tekton_pipelines_controller_taskruns_pod_latency_milliseconds uses _milliseconds suffix while other duration metrics use _seconds

Resource Attributes & Configuration

Level 1 — Aligned
▼

What we observed

Tekton sets only service.name natively on traces — pipelinerun-reconciler and taskrun-reconciler. No service.version, service.namespace, service.instance.id, or telemetry.sdk.* attributes are set by Tekton itself on traces.

The same physical process emits traces with service.name = pipelinerun-reconciler or taskrun-reconciler, while metrics carry service.name = tekton-pipelines-controller — three different identity values for one process. This inconsistency prevents backend-level correlation using service.name as a join key. Configuration is exclusively via Kubernetes ConfigMaps; no OTEL_* environment variables are supported.

What's working well

  • service.name is set natively on traces via semconv.ServiceNameKey.String(service)
  • service.name is present on metrics (via Prometheus label)
  • After collector enrichment, rich Kubernetes metadata is available: k8s.pod.name, k8s.namespace.name, k8s.deployment.name, etc.

Opportunities

  • Align service.name across traces and metrics — use a single consistent value like tekton-pipelines-controller
  • Add service.version (semver, not commit hash) to the trace resource
  • Support standard OTEL_SERVICE_NAME, OTEL_EXPORTER_OTLP_ENDPOINT, and OTEL_RESOURCE_ATTRIBUTES env vars alongside ConfigMap configuration
  • Add service.instance.id to trace resources for pod-level correlation

Checklist

  • service.name is set natively on traces
  • service.name is present on metrics (via Prometheus label)
  • service.name is inconsistent between traces and metrics for the same process
  • service.version is absent from traces
  • No OTEL_* environment variable support
  • telemetry.sdk.* attributes absent from traces (present in metrics as Prometheus labels only)
  • No service.instance.id on traces

Trace Modeling & Context Propagation

Level 2 — Native
▼

What we observed

Tekton produces coherent, hierarchical traces that tell a complete story of a PipelineRun execution. A full PipelineRun trace (aed6aad...) contained 610 total spans including 51 TaskRun:ReconcileKind spans as children of createTaskRun — achieved via Kubernetes annotation-based span context propagation (tekton.dev/taskrunSpanContext). W3C Trace Context (traceparent/tracestate) is used exclusively.

The trace hierarchy spans: PipelineRun:Reconciler → PipelineRun:ReconcileKind → reconcile → runNextSchedulableTask → createTaskRun → TaskRun:ReconcileKind → prepare → createPod. Standalone TaskRuns produce their own root traces correctly. All 1,262 spans use kind=1 (INTERNAL).

What's working well

  • W3C Trace Context propagation via propagation.TraceContext{}
  • Sophisticated cross-reconciler propagation via Kubernetes annotations — a creative solution to a genuinely hard distributed tracing problem
  • Trace structure reflects the actual execution model (reconcile loops, task creation, pod scheduling)
  • Root spans carry meaningful context: resource name + namespace
  • Standalone TaskRun and PipelineRun traces are correctly modeled as separate root traces

Opportunities

  • Add pipelinerun/taskrun + namespace attributes to child spans — currently 1,137 child spans have no attributes
  • Consider using appropriate span kinds for controller entry points (e.g., CONSUMER for event-driven reconcile loops)
  • Set a version on instrumentation scopes (PipelineRunReconciler, TaskRunReconciler)

Checklist

  • W3C Trace Context propagation
  • Root spans have meaningful attributes (resource name + namespace)
  • PipelineRun→TaskRun cross-reconciler context propagation via Kubernetes annotations
  • Trace structure reflects the actual execution model (reconcile loops, task creation)
  • Standalone TaskRun and PipelineRun traces are correctly modeled
  • All spans use INTERNAL kind (no SERVER/CLIENT spans for the controller's entry points)
  • Child spans have no attributes — cannot filter or aggregate on pipeline/task dimensions at the span level
  • Instrumentation scope has no version

Multi-Signal Observability

Level 1 — Aligned
▼

What we observed

Two signals are natively first-class: traces (OTLP HTTP) and metrics (Prometheus scrape, with OTLP export available). Logs are stdout-only with no OTLP export. The dual-protocol model creates an operational split: traces flow through one pipeline path, metrics through another.

Cross-signal correlation is hampered by inconsistent service.name: the controller emits traces with service.name = pipelinerun-reconciler or taskrun-reconciler, but metrics carry service.name = tekton-pipelines-controller. An operator cannot navigate from a trace to the corresponding metrics using service.name as a join key without knowing this mapping. No trace context fields (trace_id, span_id) appear in logs or metrics exemplars.

What's working well

  • Two signals (traces + metrics) are natively first-class and flowing
  • Metrics are rich and actionable — duration histograms, counters, gauges with meaningful labels
  • Both signals are documented in official project documentation

Opportunities

  • Align service.name across traces and metrics — this is the highest-impact change for enabling backend correlation
  • Add OTLP log export to complete the three-signal story
  • Inject trace_id/span_id into structured log output (zap fields) to enable log-trace correlation even without OTLP logs
  • Consider adding metric exemplars linking to trace IDs on key duration histograms

Checklist

  • Two signals (traces + metrics) are natively first-class
  • Metrics are rich and actionable (duration histograms, counters, gauges with meaningful labels)
  • No OTLP logs
  • service.name is inconsistent between traces and metrics (prevents correlation)
  • No trace context (trace_id, span_id) in log output
  • Metrics do not carry exemplars linking to traces

Audience & Signal Quality

Level 2 — Native
▼

What we observed

Span names are logical CI/CD operations that are meaningful to platform operators without needing to understand Tekton's Go source code: PipelineRun:Reconciler, PipelineRun:ReconcileKind, reconcile, resolvePipelineState, runNextSchedulableTask, createTaskRun, prepare, createPod, stopSidecars, finishReconcileUpdateEmitEvents.

The 11 Tekton-specific metrics are all actionable: duration histograms for PipelineRuns and TaskRuns (with status, pipeline, task, namespace labels), running counts, and pod scheduling latency. One known quality issue: tekton_pipelines_controller_taskruns_pod_latency_milliseconds has unbounded cardinality due to task and taskrun labels (tracked in issue #9393).

What's working well

  • Span names represent logical CI/CD operations, not internal function names
  • Root spans carry meaningful context (resource name + namespace)
  • Metrics have actionable labels: status, pipeline, task, namespace
  • Metrics are documented with type, labels, and stability status in docs/metrics.md
  • Trace structure is coherent and useful without backend customization

Opportunities

  • Add pipelinerun/taskrun/namespace attributes to child spans to enable filtering in trace backends like Jaeger or Tempo
  • Remove or rename durationAndCountMetrics span — it represents an internal implementation detail, not a user-visible operation
  • Address the unbounded cardinality issue in tekton_pipelines_controller_taskruns_pod_latency_milliseconds (issue #9393)
  • Integrate logs into the OTLP pipeline for a complete observability story

Checklist

  • Span names represent logical CI/CD operations, not internal function names
  • Root spans carry meaningful context (resource name + namespace)
  • Metrics have actionable labels (status, pipeline, task, namespace)
  • Metrics are documented with type, labels, and stability status
  • Trace structure is coherent and useful without backend customization
  • Child spans have no attributes — limits filtering in trace backends
  • durationAndCountMetrics span is an internal implementation detail exposed as a span
  • tekton_pipelines_controller_taskruns_pod_latency_milliseconds has unbounded cardinality (known issue #9393)
  • No logs in the OTLP pipeline

Stability & Change Management

Level 2 — Native
▼

What we observed

Tekton provides dedicated telemetry documentation: docs/metrics.md (complete metric reference with name, type, labels, and stability status — all core metrics marked experimental) and docs/metrics-migration-otel.md (comprehensive OpenCensus→OpenTelemetry migration guide with before/after tables, per-category impact levels, and an explicit "Action Required" section).

The schema URL https://opentelemetry.io/schemas/1.12.0 is set natively on trace resources via semconv.SchemaURL from the semconv/v1.12.0 import — but this version is outdated (current stable is v1.26.0). No stability guarantee exists for span names or attributes. Release notes reference telemetry-related changes including OTel SDK bumps.

What's working well

  • Metrics are documented with a complete reference table in docs/metrics.md
  • Breaking telemetry changes are documented with migration guides — the OpenCensus→OTel migration guide is exemplary
  • Schema URL is set natively on trace resources
  • Metrics have explicit stability labels (experimental)
  • Release notes reference telemetry-related changes (e.g., PR #9641, #9757)

Opportunities

  • Update the semconv import from v1.12.0 to v1.26.0+ to keep the schema URL current
  • Graduate core duration and count metrics from experimental to stable to give operators a reliability guarantee
  • Document a formal stability contract for span names and attributes
  • Document the OTEL_* env var configuration contract (or explicitly state it's not supported) in the observability docs

Checklist

  • Metrics are documented with a complete reference table
  • Breaking telemetry changes are documented with migration guides
  • Schema URL is set natively on trace resources
  • Metrics have explicit stability labels (experimental)
  • Release notes reference telemetry-related changes
  • Schema URL references outdated semconv v1.12.0 (not current v1.26.0)
  • No stability guarantee for span names or attributes
  • No schema URL on metrics
  • No OTEL_* env var configuration contract documented
Key Takeaways

Strengths

  • Cross-reconciler trace propagation via Kubernetes annotations — architecturally elegant solution to a genuinely hard distributed tracing problem
  • Rich, actionable CI/CD metrics with pipeline, task, status, and namespace dimensions
  • Dual OTLP export paths for both traces and metrics give operators architectural flexibility
  • Exemplary breaking-change communication — the OpenCensus→OTel migration guide is a model for the ecosystem
  • Current OTel SDK (v1.43.0) with logical, operator-friendly span names

Priority Improvements

  • Align service.name across traces (pipelinerun-reconciler) and metrics (tekton-pipelines-controller) — highest-impact change for enabling backend correlation
  • Add attributes to child spans — 1,137 spans carry no attributes, limiting filtering and aggregation in trace backends
  • Add service.version (semver) to trace resources and update semconv import to v1.26.0+
  • Support standard OTEL_* environment variables alongside ConfigMap configuration
  • Add OTLP log export (opt-in) to complete the three-signal observability story

Notable Observations

  • The Kubernetes annotation-based span context propagation (tekton.dev/taskrunSpanContext) is a unique and noteworthy pattern for other Kubernetes controller authors
  • Despite using OTel SDK v1.43.0, the tracing code imports semconv/v1.12.0 — a maintenance gap that could be updated without changing any attribute names
  • All core metrics are marked experimental — good transparency, but graduating key metrics to stable would benefit the ecosystem
  • Mixed metric unit suffix: _milliseconds on pod latency vs _seconds on all other duration metrics creates dashboard friction
Methodology: Telemetry collected using an OpenTelemetry Collector with file export (fileexporter) in a local kind cluster (otel-eval-tekton). The k8sattributes processor enriched telemetry with Kubernetes metadata. Traces collected via OTLP HTTP receiver; metrics via Prometheus receiver (scraping four Tekton service endpoints). Test workloads: 6 standalone TaskRuns (hello-world-1 through hello-world-6), 1 multi-step TaskRun (multi-step-1), and 1 PipelineRun (demo-pipeline-run-1) with 4 tasks. Source code reviewed: pkg/tracing/tracing.go, pkg/reconciler/pipelinerun/tracing.go, pkg/reconciler/taskrun/tracing.go, pkg/apis/config/metrics.go. Semantic conventions checked against the OpenTelemetry specification (stable, early 2025).
